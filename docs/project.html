How MUJ Mess
is built.

One annual fee, two messes, and a choice at every meal. Students book where they'll eat. The database works out what each kitchen should cook, who actually came, and what goes to NGOs.

01The problem

MUJ has two messes, BluDove and BluSpring, with the same fee (about ₹79,000 a year). Today a student picks one and is stuck there for at least two months. The kitchens guess how many people will come, so food runs out or gets thrown away.

What students get

  • Pick BluDove, BluSpring or skip, for each of breakfast, lunch, hi-tea and dinner, up to 7 days ahead.
  • Pause the mess when going home. Those meals aren't cooked.
  • Log in with a phone number and a one-time code (OTP).

What the messes get

  • An exact head count per meal, plus a 30% buffer for walk-ins.
  • A counter screen to mark who was served.
  • After each meal, leftovers are assigned to an NGO automatically.

02Architecture

Three layers. The browser never talks to the database directly; it calls an API, and the API is the only program with a database login.

Why an API in the middle?

A web page is public, so it can't hold a database password. The API checks who you are, checks the rules, and then runs a fixed, parameterized SQL statement. This is the usual 3-tier design: presentation, application, data.

Code layers

main.py handles requests (controller) → auth.py does login → repo.py holds every SQL statement (repository pattern) → MySQL enforces the rules again with constraints and triggers.

03ER diagram

Each arrow goes from a foreign key (the "many" side) to the primary key it points to (the "one" side). PK = primary key, FK = foreign key, UQ = unique.

activity_log (not drawn) is an audit table that only triggers write to. It has no foreign key on purpose, so the history stays even if other data changes.

04Tables and normalization

Every fact is stored once. Things that can be calculated, like "how many to cook", are views, not stored columns.

TableOne row is…Keys and rules
messesa mess (BluDove, BluSpring)PK, UNIQUE name
meal_slotsa meal with its time windowPK, UNIQUE code, CHECK ends > starts
menu_itemsone dish of one mess at one meal2 FKs, UNIQUE (mess, slot, dish)
studentsa student, identified by phoneUNIQUE phone, CHECK 10-digit Indian mobile
otp_codesone login code sentonly a keyed hash is stored; expiry; attempt counter
bookingsa student's choice for one meal on one day3 FKs, UNIQUE (student, date, slot), ENUM status, CHECK status ↔ mess
pausesa period the student is awayFK, CHECK to ≥ from
attendancea student actually served3 FKs, UNIQUE (student, date, slot): can't eat twice
ngosa partner NGO or shelterUNIQUE name
donationsleftover from one mess and meal, given to one NGO3 FKs, UNIQUE (date, slot, mess)
activity_logone event (login, booking, served…)written only by triggers
1NF: every cell holds one value. Dishes are separate rows in menu_items, not a comma-separated list. Each student's 4 daily meals are 4 rows, not 4 columns.
2NF: no column depends on only part of a key. bookings is identified by (student, date, slot). The mess name isn't stored there, only mess_id, because the name depends on the mess and not on the booking.
3NF: no column depends on another non-key column. A student's phone lives only in students, and meal times only in meal_slots. Counts like cook_for and donate are calculated in views, so they can never get out of sync.

05Triggers

Code inside the database that runs by itself when a row changes. We use them for two jobs: an audit trail, and a business rule that even a buggy app can't get around.

TriggerWhenDoes
trg_booking_paused_ins / _updBEFORE INSERT / UPDATE on bookingsRefuses the booking with SIGNAL SQLSTATE '45000' if the student is paused that day. The API turns this into "Your mess is paused for this date".

trg_booking_log_ins, trg_booking_log_updAFTER INSERT / UPDATE on bookingsLogs BOOK, SKIPPED, CHANGE (old mess → new mess) and PAUSED.
trg_pause_log, trg_resume_logAFTER INSERT / UPDATE on pausesLogs PAUSE and RESUME.

-- The database itself refuses a booking while the student is away.
CREATE TRIGGER trg_booking_paused_ins BEFORE INSERT ON bookings FOR EACH ROW
BEGIN
  IF NEW.status = 'booked' AND EXISTS (
       SELECT 1 FROM pauses p
       WHERE p.student_id = NEW.student_id
         AND NEW.meal_date BETWEEN p.from_date AND p.to_date
         AND (p.ended_on IS NULL OR NEW.meal_date < p.ended_on)) THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Your mess is paused for this date';
  END IF;
END

06Stored procedures and transactions

Each procedure is one transaction: every step happens, or none do. If anything fails, the handler runs ROLLBACK and passes the error back up.

sp_pause_mess(student, from, to)

Adds the pause and changes every booking in that range to paused, so the kitchens stop counting the student. Both steps or neither.

sp_resume_mess(student, today)

Ends running and future pauses from today, and turns released meals back into skipped so the student can book again.

sp_close_meal(date, slot)

Run by staff when a meal ends. A cursor loops over each mess's leftover in v_meal_summary and assigns it to the NGO that has received the least so far, so donations are spread fairly. Running it again recalculates instead of adding twice.

CREATE PROCEDURE sp_pause_mess(IN p_student INT, IN p_from DATE, IN p_to DATE)
BEGIN
  DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END;
  START TRANSACTION;
    INSERT INTO pauses (student_id, from_date, to_date) VALUES (p_student, p_from, p_to);
    UPDATE bookings SET status = 'paused', mess_id = NULL
    WHERE student_id = p_student AND meal_date BETWEEN p_from AND p_to;
  COMMIT;
END

07Views and the food math

A view is a saved SELECT that you can query like a table. The kitchens' numbers are views, so they're always current.

ViewShowsSQL used
v_daily_forecastbooked heads and cook_for = CEIL(booked × 1.3) per mess and mealJOIN, GROUP BY, COUNT, CEIL
v_meal_summarybooked, cooked, served, no-shows, walk-ins, buffer left, donateUNION, derived tables, LEFT JOIN, correlated EXISTS, GREATEST/LEAST
v_live_bookingseveryone's choices, newest firstJOIN, LEFT JOIN, COALESCE
v_ngo_totalsdeliveries and portions per NGOLEFT JOIN, SUM, COUNT

cook = booked × 1.3  ·  buffer left = buffer − walk-ins
donate = buffer left + 50% of no-shows' portions

Worked example: BluDove breakfast. 30 booked → cook 39 (buffer 9). 28 were served, and 1 of them was a walk-in, so 27 booked students came and 3 didn't. Buffer left = 9 − 1 = 8. Donate = 8 + ⌊3 × 0.5⌋ = 9 portions. The donation can never be more than what is actually left (39 − 28 = 11).

08The life of one booking

What happens in about 50 ms when a student taps "BluSpring" for dinner.

  1. The browser sends POST /bookings with the login token: {meal_date, slot_id: 4, mess_id: 2}.
  2. FastAPI checks the token signature and validates the body (date within 7 days, the meal and mess exist).
  3. repo.py runs INSERT … ON DUPLICATE KEY UPDATE with parameters. The UNIQUE key means re-booking replaces the old choice.
  4. The BEFORE trigger checks for a pause. If the student is away, the whole statement is refused.
  5. The AFTER trigger writes BOOK (or CHANGE BluDove → BluSpring) into activity_log.
  6. The transaction commits. v_daily_forecast already includes the new head, and the website's "Cooking today" counter updates within 5 seconds.

09Security choices

SQL injection: not possible

Every query in repo.py uses %s placeholders. Values are sent separately from the SQL text, so user input is never pasted into a query.

Least privilege

The API logs in as mess_app, which can only SELECT, INSERT, UPDATE, EXECUTE. It can't DELETE, DROP or ALTER anything.

OTPs are never stored

Only an HMAC-SHA256 of each code is saved. Codes expire in 5 minutes, work once, and allow 5 tries. The demo shows the code on screen because sending SMS in India requires DLT registration.

Signed login tokens, staff PIN, masked phones

Tokens are HMAC-signed and expire after 7 days. Staff actions need a PIN. The public dashboard shows phones as 98xxxxx210.

11Viva questions

Questions an examiner is likely to ask, with short answers in your own words.

Why MySQL and not a NoSQL database?

The data is relational: students, meals and messes are linked by foreign keys, and the rules (one choice per meal, no booking while paused) are constraints and transactions. Those are exactly what an RDBMS guarantees.

What is the primary key of bookings, and why is there also a UNIQUE key?

The primary key is a surrogate id, which keeps joins simple. The natural key (student_id, meal_date, slot_id) is enforced with UNIQUE, so one student can't hold two choices for the same meal. Re-booking uses ON DUPLICATE KEY UPDATE to change the existing row.

Why is mess_id allowed to be NULL in bookings?

NULL means "not eating" (skipped or paused). The CHECK (status = 'booked') = (mess_id IS NOT NULL) keeps the two columns consistent: a booked row must have a mess, and a skipped row must not.

What is the difference between a trigger and a stored procedure?

A trigger runs automatically when a row is inserted, updated or deleted, and we never call it. A procedure runs only when called (CALL sp_close_meal(...)), can take parameters, and can contain a full transaction with loops and cursors.

Why BEFORE for the pause check and AFTER for logging?

BEFORE runs before the row is written, so it can stop the write with SIGNAL. AFTER runs only once the write has succeeded, so we never log something that didn't happen.

What happens if the server crashes in the middle of pausing?

sp_pause_mess is one transaction. Either the pause and all the booking updates are committed, or InnoDB rolls everything back. There's never a pause without its bookings released. That's atomicity, the A in ACID.

Why are cook_for and donate views and not columns?

They are derived from other data. Storing them would duplicate facts and could go stale whenever a booking changes. That breaks 3NF and causes update anomalies. A view calculates them fresh on every query.

How do you prevent SQL injection?

Parameterized queries. The SQL text has placeholders (%s) and the driver sends the values separately, so input like ' OR 1=1 -- is treated as a plain string, never as SQL.

Which indexes did you add, and why?

UNIQUE keys create indexes automatically. We also added idx_forecast (meal_date, slot_id, mess_id, status) to match the GROUP BY in the forecast view, idx_otp_phone for the latest-OTP lookup, and idx_att_meal for the attendance summary.

What is a walk-in and how is it detected?

A student served at a mess where they didn't book. A correlated EXISTS subquery checks for a matching booked row. Walk-ins eat from the 30% buffer.

Why doesn't otp_codes have a foreign key to students?

An OTP is sent before the student exists: their first login creates the student row. So OTPs are keyed by phone. The same goes for activity_log: it's an audit history and must outlive changes to other tables.

How is the NGO chosen in sp_close_meal?

It's a LEFT JOIN of ngos to donations, grouped by NGO and ordered by COALESCE(SUM(portions), 0), taking LIMIT 1. The NGO that has received the least gets the next donation. An NGO with nothing yet has a sum of 0 thanks to the LEFT JOIN.
